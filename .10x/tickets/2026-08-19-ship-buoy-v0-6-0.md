# Ship Buoy v0.6.0 and Establish Reusable Releases

## Outcome

Replace the paused, per-version manual ceremony with one reusable,
least-privilege GitHub Release workflow and use it to publish Buoy v0.6.0.
Future releases use the same reviewed release-preparation change followed by
one annotated tag push; they do not require a new release decision or manual
artifact ceremony. Their ordinary post-run closure is records-only and does
not gate or mutate the public Release.

## Scope

- Date and validate the v0.6.0 changelog section, README asset URL, and
  supported-version row.
- Replace the paused Release workflow with an annotated-tag-triggered test,
  build, attestation, draft-verification, and publication pipeline.
- Keep CI and release-readiness read-only and retain the four readiness check
  names.
- Generalize the source and distribution validator to the latest reviewed
  stable changelog version.
- Record and supersede the unused one-time v0.6.0 procedure without deleting
  its audit history.
- Integrate through `develop`, promote the reviewed tree to `main`, enable
  repository immutable Releases, and push one annotated v0.6.0 tag at the
  exact passing main commit.

No application behavior, dependency, lockfile, package version authority,
PyPI publication, provider/model/data operation, real Buoy-home access, or
unrelated repository setting is in scope.

## Execution

1. Implement and independently review the bounded source, workflow, tests,
   and governing records from exact
   `develop@06708ce39e9b5e8c15ce6204c2af4e9c73334ade`.
2. Pass focused validation, locked Python 3.11 and 3.13 full suites, source,
   ranking, C6, lock, distribution, workflow-lint, and diff-hygiene gates.
3. Publish one exact-head task PR and have a separate integration role
   squash-merge it into the still-current develop base.
4. Promote that exact develop head through a release-readiness PR and merge
   commit it into the still-current
   `main@caed68fdce3ef91e41c11f5d586a6166837d0392`.
5. Require exact-main CI, confirm local/remote v0.6.0 tag and Release absence,
   and enable repository immutable Releases through the owner-admin setting.
6. Create and push one annotated `v0.6.0` tag with message `Buoy v0.6.0` at
   that exact main commit. The workflow performs every artifact and Release
   write.
7. Verify the workflow, immutable/latest Release, exact two assets, asset and
   release attestations, and a clean downloaded-wheel installation.
8. Record the hosted result, move this ticket to `tickets/done`, mark evidence
   recorded, and add a final review through a records-only change with no
   hosted Release mutation.

## Acceptance

- The reusable workflow is pinned, defaults to `contents: read`, and grants
  only its publication job exact `contents: write`, `id-token: write`, and
  `attestations: write`.
- The tag must be annotated, match the latest reviewed changelog version and
  message, peel to current `main`, and encounter no conflicting Release.
- Python 3.11/3.13 tests and exact distribution validation pass before any
  Release is created.
- The published v0.6.0 Release is latest and immutable and contains only
  `buoy_search-0.6.0-py3-none-any.whl` and
  `buoy_search-0.6.0.tar.gz`; API digests, sizes, numeric-ID downloads, and
  attestations verify.
- The downloaded wheel reports 0.6.0 and passes CLI/module/telemetry/tokenizer
  smoke checks in an isolated home.
- Exact completed reruns are verification-only; mismatched or partial state
  fails without deletion, replacement, clobber, force, or PyPI publication.
