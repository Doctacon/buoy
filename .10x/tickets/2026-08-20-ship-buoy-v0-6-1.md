# Ship Buoy v0.6.1 Through the Reusable Publisher

## Outcome

Publish Buoy v0.6.1 as the first successful invocation of the accepted
annotated-tag-triggered GitHub Release workflow. Preserve the failed v0.6.0
tag and run permanently, correct the one tag-context test-fixture defect, and
use the normal release path without a recovery workflow or manual dispatch.

## Scope

- Advance the staged public release surfaces from unpublished v0.6.0 to
  v0.6.1: dated changelog heading/comparison link, README wheel URL,
  supported-version row, and validator expectations.
- Make
  `DynamicVersionTests.test_clean_editable_install_derives_development_version_from_vcs`
  hermetic by constructing controlled empty post-tag history before asserting
  a development version. Preserve the stable-version behavior at exact tags.
- Integrate the bounded task through an exact-head PR to `develop`, then use a
  reviewed `develop`-to-`main` release PR merged with a merge commit.
- Require exact-main CI, continued immutable-Releases enablement, and fresh
  absence of a v0.6.1 tag or Release before one annotated tag push.
- Let the existing tag-triggered workflow exclusively test, build, attest,
  draft, verify, and publish the immutable/latest v0.6.1 Release.
- Close with a separately reviewed records-only change after hosted
  verification; closure performs no tag, Release, asset, or attestation write.

No recovery or `workflow_dispatch` workflow, v0.6.0 tag movement/deletion,
application behavior, dependency, lockfile, package-version authority, PyPI
publication, provider/model/data operation, real Buoy-home access, global tool
replacement, branch-protection change, or unrelated hosted mutation is in
scope.

## Execution

1. Implement only the public v0.6.1 surfaces, hermetic fixture, and governing
   records on `work/ship-buoy-v0-6-1` from current `develop`.
2. Pass focused release-automation validation, locked Python 3.11 and 3.13
   full suites, source/ranking/C6/lock checks, distribution validation,
   Actionlint, local-link/status checks, and diff hygiene.
3. Obtain independent review, publish one exact-head task PR, and have a
   separate integration role squash-merge it into still-current `develop`.
4. Promote that exact develop head through the four release-readiness checks
   and a separate-role merge commit into still-current `main`.
5. Require exact-main ordinary CI. Reverify the unchanged v0.6.0 annotated
   tag and failed run, enabled immutable Releases, and complete absence of a
   local/remote v0.6.1 tag and any v0.6.1 Release including drafts.
6. Create and push one annotated `v0.6.1` tag with message `Buoy v0.6.1` at
   that exact main commit. The normal reusable workflow performs every
   artifact and Release write.
7. Verify the successful workflow, exact annotated tag, immutable/latest
   Release, exact two assets, API sizes/digests, numeric-ID downloads, build
   attestations, and isolated downloaded-wheel smoke.
8. Record final identities/effects and close the ticket/evidence through the
   ordinary separately reviewed records-only develop/main path without any
   new tag or Release mutation.

## Acceptance

- The hermetic test fixture passes on ordinary branch history and at an exact
  stable release tag without weakening the public stable-version assertion.
- The pre-existing v0.6.0 tag object
  `1ffb70f5656f48c782defbe252dab44426134343` remains byte-for-byte fixed and
  no v0.6.0 Release, asset, or attestation is created.
- The public v0.6.1 tag is annotated, peels to exact passing current `main`,
  and triggers the normal workflow with no manual dispatch or recovery path.
- The published Release is latest and immutable and contains only
  `buoy_search-0.6.1-py3-none-any.whl` and
  `buoy_search-0.6.1.tar.gz`; API digests, sizes, numeric-ID downloads, and
  build attestations verify.
- The downloaded wheel reports `buoy 0.6.1` and passes CLI, module,
  telemetry-help, import, and tokenizer smoke in a fresh isolated home.
- Only an exact rerun after the matching Release is already successfully
  published is verification-only. Any failed run or partial hosted state is
  STOP for read-only inspection before the owner chooses a separately
  reviewed next action; no blind rerun, delete, replace, clobber, force, tag
  movement, PyPI, application, provider, or user-home operation occurs.
